### 1.3.2 `src/logic.js` — exact current exports (verified 2026-08-29)

All pure functions, no DOM access, imported from `data.js`:

- **`getApplicableModules(profile)`** — returns `['base']` plus `'nonprofit'` if `profile.orgType === 'nonprofit'` plus `'youth'` if `profile.servesYouth === true`. This is the entire current "routing" logic — far short of the full overlay stack described in the research foundation §12.1 (jurisdiction, industry, data-type, org-type, youth, customer-type, maturity, size, tool-derived). Only org-type and youth are implemented today; everything else in that stack is unbuilt (**B11**).
- **`getQuestionsForAssessment(profile, depth)`** — pools base+nonprofit+youth questions per applicable modules, filters by `depths.indexOf(depth) !== -1`.
- **`computeScores(questions, answers)`** — sums per-function (govern/map/measure/manage), each question worth up to 3 points (`max += 3` per answered question), `overall = round((totalSum/totalMax)*100)`. **This is the current flat-percentage scoring** that R2 and the research foundation §8.2 recommend replacing with the 5-sub-dimension weighted model — see §1.4.5 below. Not yet changed.
- **`computeTier(overall)`** — 3-tier risk bucketing on the *overall percentage*: ≥70 "Lower risk," ≥40 "Moderate risk," else "Higher risk." **Important: this is a different "tier" concept from the four-tier per-use-case AI system risk model (Tier 1–4) described in the research foundation §8.4 and refined by R3.** The current `computeTier` buckets the organization's overall readiness score into three risk bands; the four-tier model classifies individual AI use cases/tools by inherent risk. Both are needed; they are not the same thing, and B6/B7 need to keep this distinction straight when building the new risk-tiering module.
- **`GAP_THRESHOLD = 20`** and **`computeConfidenceGap(scores, confidenceAnswers)`** — compares self-reported Likert confidence against the evidence-based score per function; flags `'overconfident'`/`'underconfident'`/`'aligned'` if the gap is ≥20 percentage points either direction. A real, already-shipped feature — not mentioned much in the research docs but worth knowing it exists and works.
- **`identifyGaps(questions, answers)`** — flags any answer ≤1 (of 0–3) as a gap, priority `'high'` if 0, `'medium'` if 1.
- **`buildRecommendations(gaps)`** — dedupes by question id, orders high-priority gaps before medium, looks up `REC_TITLES`/`REC_BODIES` with the generic-fallback behavior noted above.
- **`classifyToolsInUse(selectedToolIds, otherTools)`** — buckets selected tools into `{'high-risk':[], 'caution':[], 'lower-risk':[]}` by looking up `TOOL_MASTER_LIST`.
- **`filterToolsForProfile(profile)`** — returns tools where `industries` includes `'all'` or the profile's specific industry.
- **`hasIndustryOverlay(profile)`** — **currently hardcoded to always return `false`**, with an in-code comment stating v2 has no industry-specific overlays built (only nonprofit/youth, which are treated as independent modules, not industry overlays). This is a real, honestly-flagged gap — not a bug, a known scope boundary.
- **`scopeSubject(scopeId)`** — returns 'your department' / 'this initiative' / 'your organization' for the `{subject}` token in confidence questions.
- **`describeScope(scope)`** and **`applyScopeFraming(recs, scope)`** — produce the human-readable scope description and append scope-specific framing text to recommendation bodies (department: "confirm with whoever owns policy for the full org"; initiative: "treat as pre-deployment review").

### 1.3.3 What this means concretely for anyone picking up build work

The existing code is **well-tested, honestly documented, and architecturally sound as far as it goes** — 88 unit tests, 90%+ enforced coverage, CI on every push, in-code comments that candidly flag scope limitations (`hasIndustryOverlay` always false, base questions have no `REC_BODIES` entries, only nonprofit/youth are real modules). It is not a prototype to be thrown away; it is a solid v2 foundation that the entire redesign discussed in this Cowork thread (§1.4) extends and partially replaces. Anyone starting build work should run `npm test` and `npm run test:e2e` before and after any change, and should expect the 90% coverage gate to fail the build if new logic isn't tested — this is a hard CI gate, not a suggestion.

## 1.4 The target architecture — every design decision made in this Cowork thread

This is the redesign this whole project (R1–R22, B1–B24) is working toward. None of it is built yet except B1 (artifact retirement). It was arrived at over several turns of discussion; the reasoning behind each decision is preserved here so it doesn't have to be re-litigated.

### 1.4.1 Three respondent types, one assessed subject

The tool assesses one thing regardless of who's answering: **"how ready is the AI governance program in this organization" — filtered through the respondent's own vantage point.** Three respondent types:

1. **Leadership/executive** (CEO, CMO, board member, etc.) — org-wide visibility, strategic/accountability framing.
2. **Department/function** (e.g. marketing & communications) — visibility scoped to their function, may not see org-wide policy that exists above them (this is exactly the failure mode the existing `department` scope option already partially addresses — see §1.3.1 — but the *role* axis is new and independent of it).
3. **Individual employee** — the newest addition (added mid-thread, after the original 5 requirements were first confirmed). **Standalone by design — "can belong to any department."** Explicitly **not** meant to be scoped only to leadership or only to a named department; it's a distinct, independent respondent lane. Kartik confirmed the employee respondent type should carry a **department field** (optional/selectable) specifically so the assessment content can be tailored to that employee's department context, even though the respondent type itself is standalone and department-agnostic in identity.

**Critical distinction Kartik made explicitly and that must not be lost:** role (who's answering) and assessment scope (org/department/initiative, §1.3.1's `SCOPE_OPTIONS`) are related but not the same axis. A department-scoped *assessment* could still be answered by a leadership-type respondent (a VP answering only for their own department) or by an individual-employee-type respondent in that department. **Role is being added as one more modifier in the existing overlay stack (§12.1 of the research foundation), not a parallel or replacement system for scope** — this is B11's job. B3 is about reconciling/retiring the *current, narrower* org/department/initiative selector against this richer combined model, not deleting the concept of scope entirely.

### 1.4.2 Standalone default + entity registration → comparison feature

**Standalone assessment stays the default experience** — no signup, no backend, exactly like today. **Entity registration is an opt-in unlock**: once an organization registers as an entity, subsequent assessments taken under that entity are automatically collected and compared in the backend, producing a cross-role comparison report (e.g. leadership's self-assessment vs. what employees across departments actually report) without any manual aggregation step. Kartik's own framing: *"anyone taking the assessment will automatically collect and compare the different responses in the backend and gives a report/assessment accordingly."*

When asked how to build the comparison mechanism, Kartik chose **"Add a real backend"** (over a no-backend alternative) via `AskUserQuestion` earlier in this thread — this is a committed decision, not still open. This is why B18–B22 (backend infra, API layer, comparison computation, comparison UI, hosting) exist as a distinct Low-priority Build tier: it's real, wanted work, deliberately sequenced last because it depends on everything else (data model, scoring, role modifier, item bank) being stable first, not because it's less important.

### 1.4.3 Role-adaptive question bank, chosen as the build-order priority

When asked to choose a build-order priority, Kartik chose **"Role-adaptive question bank first"** over alternatives, also via `AskUserQuestion` earlier in this thread. This is why the research and build sequencing in Part 2 below front-loads the item bank / NIST gap-closing work (R1, R8, B8, B9) rather than, say, the backend or the report redesign.

The concrete critique that motivated this: **a marketing/communications respondent currently gets identical questions to a CEO or CMO** — the existing 31-question bank has no role-awareness at all. Kartik's proposed fix, now the committed design: **30–40 questions per category in an item bank, with a per-assessment subset (a "test blueprint") selected based on role × assessment type**, rather than a fixed 20-question base set shown to everyone. This is explicitly **item banking, not full computerized adaptive testing (CAT)/IRT** — a real, deliberate methodology distinction established in this thread's research: item banking (larger tagged pool, fixed-length form assembled via a blueprint) is the right-sized approach; full IRT-calibrated CAT would need item-response-theory calibration data this tool will never have at its scale, and was explicitly rejected as overkill.

### 1.4.4 Answer format: Behaviorally Anchored Rating Scale (BARS), never free text

Separately from question *content*, Kartik raised answer *format* as its own bias-reduction lever — explicitly flagging that free-text boxes are bad for time-constrained leadership respondents (people won't finish them) and that response wording itself should be tweaked to reduce social-desirability bias ("a person taking this assessment would probably figure out what the correct answer is"). The research response, now the committed design direction:

- **Single-select, concrete, observable-state answer options — BARS format** — not free text, not a naked abstract Likert ("how would you rate your governance, 1–5") that invites a guessed "correct" answer. This is in fact **already exactly how the existing 20 base questions are written** (see the `g1`/`g2` examples in §1.3.1 — each option describes a specific observable state like "Written policy, reviewed and enforced" rather than a number on an abstract scale). All 33 of R8's new drafted items (§1.5.6) follow this same standard. The remaining new work is an explicit rewrite/audit pass (**B9**) confirming/tightening every existing question's options against the BARS standard, since some of the older base questions may have room to be sharpened.
- **Evidence-anchored wording** ("can you produce this artifact" rather than "do you feel governance is good") is the most practical, COBIT/CMMI-aligned bias lever, per this thread's research — reducing social-desirability bias more reliably than reformatting into forced-choice/ipsative formats, which were explicitly considered and rejected as overkill (they cost reliability and need complex Thurstonian IRT scoring this tool has no use for at its scale).
- Face-saving response wording is cited (per a systematic review found during this research) as the single empirically strongest lever for social-desirability bias reduction generally — worth keeping in mind when B9 does the rewrite pass.

### 1.4.5 Scoring architecture — five weighted sub-dimensions, plus three separately-reported dimensions, plus a gating rule

This replaces `computeScores()`'s current flat percentage-of-max-points calculation (§1.3.2). Per `AI_Governance_Research_Foundation_v2.md` §8.2, independently corroborated by Superblocks' "5 AI Governance Failure Modes" (R2 finding):

**Governance Maturity score (0–100), five weighted sub-dimensions:**

| Sub-dimension | Weight | What it measures |
|---|---|---|
| Ownership & Accountability | 20% | Named owner, documented responsibility, board/exec engagement |
| Inventory & Visibility | 20% | Completeness of AI system/tool inventory |
| Risk Classification | 20% | Existence and application of a use-case risk-tiering method |
| Controls & Evidence | 25% | Whether controls produce auditable artifacts (highest weight — this is what an auditor actually tests, now backed by two independent sources per R2: ISO 42001 audit-practice reporting and the "governance theater" failure mode) |
| Monitoring & Response | 15% | Ongoing monitoring, incident response, change triggers |

**Plus a gating/floor rule (R2 finding, not in the original research foundation — this is new, evidence-driven scope added mid-project):** a bottom-tier Ownership & Accountability score should **cap** the overall maturity score regardless of how the other four dimensions score, because CSA whitepaper evidence (73% of orgs report internal ownership conflict; 96% of CISOs get AI governance responsibility without authority) shows ownership functions as a *structural prerequisite* the other four dimensions depend on, not just one-fifth of a flat weighted average. **This is a genuine architecture change to B5, not a percentage tweak.** A bottom-tier Ownership & Accountability score should also independently qualify as a "critical gap" per **B7**, regardless of the other four dimensions.

**Three additional dimensions, reported separately and never averaged into the maturity score** (averaging them in "produces a number that means nothing," per the research foundation):
- **Regulatory Exposure** — composite of jurisdiction, industry, data types, customer type, AI maturity. R4/R5/R6 findings (EU Digital Omnibus, Colorado SB 26-189, Canada's actual patchwork) are the current source data for this dimension's EU/Colorado/Canada legs.
- **Tool Portfolio Risk** — derived from the declared tool inventory against `TOOL_MASTER_LIST` classifications, weighted by the org's data sensitivity.
- **Framework Coverage** — percentage alignment against NIST AI RMF (and ISO 42001/EU AI Act where relevant), reported compliant/partial/missing per area.

**If exact percentages are ever formally challenged**, the Analytic Hierarchy Process (AHP) — pairwise comparison with a consistency-ratio check — is the documented, citable methodology to re-derive them precisely. Not run this session (needs real stakeholder pairwise judgments, not something to simulate); flagged as the correct future tool if needed.

### 1.4.6 Four-tier per-use-case risk model, SMB-adapted

Distinct from `computeTier()`'s org-wide readiness bucketing (§1.3.2) — this classifies individual AI *use cases/tools*, not the organization's overall score. Per the research foundation §8.4, refined by R3:

- Keep the four-tier structure (Tier 1 Critical / Tier 2 High / Tier 3 Medium / Tier 4 Low) and its seven classification criteria (materiality, autonomy, data sensitivity, consequential decisions, population affected, reversibility, third-party dependency) — these were already sector-agnostic and didn't need fixing.
- **Replace the Tier 1/2 trigger** — the original "regulatory capital" (a banking-only concept) doesn't survive leaving financial services. Use the **EU AI Act's Annex III high-risk domains** instead: biometrics, critical infrastructure, education/vocational training, employment/worker management, essential services & benefits (public assistance, healthcare, creditworthiness, insurance, emergency dispatch), law enforcement, migration/asylum/border control, justice/democratic processes. For this tool's actual SMB/nonprofit audience, employment, education, and essential-services/benefits will do most of the work.
- **Build oversight/validation expectations as a (risk tier × company size band) lookup**, not a single universal column — crossed against the existing size-band table already present in the docx (§9.2/§5.1: 1–10 owner-led informal, 11–50 exec review, 51–200 formal board + part-time compliance role, 201–1000 dedicated governance role + board committee, 1000+ full governance function). Merge Tier 2/Tier 3 oversight language for orgs under ~200 employees — a real, independently-built SMB framework (RaftLabs) found this reflects how governance actually gets distributed at that scale (existing leadership roles absorb it, not new dedicated committees), backed by a citable stat: only 1.5% of surveyed orgs believe they have adequate governance headcount.
- The Annex III domain list is also recommended as the **first context-capture question in the New AI Tool Adoption assessment** (§1.4.7) — "does this tool's use touch any of these areas" routes straight into Tier 1/2 scrutiny.

### 1.4.7 Two distinct assessment types: Governance Readiness vs. New AI Tool Adoption

Confirmed as a real, separate assessment type (not a mode/variant of the readiness assessment) — this was independently corroborated by R1's NIST gap analysis: MANAGE 1.1 ("should this AI system's development/deployment proceed") and MANAGE 2.1 ("resources required, including viable non-AI alternatives") are *decision-point* questions that don't fit the readiness assessment's "how ready are you" framing at all — they ask "should you do this," which is what the New AI Tool Adoption assessment is *for*. This is good structural confirmation the two-assessment-type split was the right call, not just a product nicety. **B13** builds this; it depends on B6 (risk-tiering module) being done first, since the Annex III domain list from §1.4.6 is its natural first question. **R8 part 2 confirmed and acted on this finding directly**: rather than force MANAGE 1.1/2.1 into the readiness item bank, they were deliberately left undrafted there and are now earmarked as B13's first two context-capture questions — genuinely new authoring work when B13 starts, not something already sitting ready to copy in.

### 1.4.8 Interactive report

Carried forward from the original five confirmed requirements (predates this visible thread). Report architecture target is the nine-section structure from the research foundation §11.1 (Executive Summary, Assessment Overview, Governance Score Breakdown, Regulatory Exposure Profile, AI Tool Portfolio Review, Framework Coverage Mapping, Risk Register, Prioritized Recommendations, Roadmap), output as interactive HTML (primary) + PDF + structured JSON/CSV export. This is **B14**; drill-down interactivity from summary gap counts into itemized reasoning is **B15**.

### 1.4.9 Six quality standards (structural, not aspirational)

Per the research foundation §11.2, each a *testable property* of the shipped output, not a value statement: (1) every score traces to specific responses; (2) every regulatory claim cites a source with a date; (3) prioritization is genuine (stated ranking basis, not just a long list); (4) recommendations are executable at the client's actual size/maturity; (5) assumptions and limitations are stated, not buried; (6) methodology is documented well enough to be challenged. **B17** implements these structurally. R2's weighting rationale, R3's "this is an inference, not a measured stat" caveat, and R7's "no Big 4 firm publishes a comparable scored methodology" finding are all direct content for standards #5 and #6 respectively. R9's finding that the functional-visibility taxonomy is a project-specific construct distinct from academic information-visibility research (§1.4.12) is also content for standard #6 — see the B17 note in Part 2.

### 1.4.10 Why NIST AI RMF is the spine (not ISO 42001, not the EU AI Act alone)

Per the research foundation §2.1: free, the US reference standard, sector-agnostic (works across all 12+ industries without licensing), crosswalks to ISO 42001 and the EU AI Act, and is what Big 4 practices actually use as a base. The alternatives each have a disqualifying problem for this specific tool: ISO 42001 is paywalled/certification-oriented, the EU AI Act is jurisdiction-specific, and Big 4 proprietary frameworks aren't licensable (and per R7, none of them publish a comparable *scored* methodology anyway — a real differentiation point, see §1.5.5 below).

### 1.4.12 Functional-visibility tagging taxonomy (R9, validated 2026-08-29)

To let the role-adaptive item bank (§1.4.3) route the right subset of the 30–40 question pool to the right respondent, each question needs a tag describing which organizational vantage point can actually answer it with evidence — not just role (leadership/department/employee) but *functional visibility*: what kind of institutional knowledge answering it correctly requires. Four tags, validated against real AI-governance-specific org-design literature (Elevate Consult's AI Governance Operating Model & RACI framework, Knostic.ai's AI Governance Roles and Responsibilities primer) rather than assumed reasonable:

- **Strategic** (recommended rename from the original working name "enterprise-wide" — see naming note below) — questions answerable only from an org-wide leadership vantage: policy existence, board oversight, budget authority.
- **Operational** — day-to-day departmental process questions: how a specific function actually uses AI tools, whether they follow a documented workflow.
- **Technical-build** — questions requiring engineering/IT/data-science visibility: model documentation, technical control implementation, security posture.
- **Legal-compliance** — questions requiring legal/compliance/privacy-office visibility: regulatory tracking, contract review, data-processing terms.

**Naming collision caught and fixed before it reached code:** the original working name "enterprise-wide" collides conceptually with the *already-shipped* `SCOPE_OPTIONS` value `'org'` (§1.3.1) — both would read as "whole organization" to a future maintainer, despite tagging two different axes (who can see the answer, vs. what the assessment is scoped to). R9 recommends renaming to **"strategic"** before this taxonomy is wired into `src/data.js`, to keep the role/visibility axis (§1.4.1) and the scope axis (§1.3.1) unambiguous from each other in code, not just in this doc.

**No case found for a fifth tag** — the four-cluster taxonomy is a good structural fit; nothing in the sourced literature suggested a gap.

**A construct that looks related but is NOT supporting evidence:** the academic "Information Visibility Scale" (ter Hoeven, Stohl, Leonardi & Stohl, 2021, *Management Communication Quarterly*) measures something genuinely different — Availability/Approval/Accessibility dimensions of general information visibility in organizations — and does not distinguish strategic/operational/technical/compliance levels at all. It must not be cited as supporting evidence for this taxonomy; it was evaluated and correctly ruled out during R9, not overlooked.

**This tag is orthogonal to respondent type (§1.4.1), not a restatement of it** — a department respondent could still need to answer a "technical-build" question if their department is engineering, and an employee respondent's department field (§1.4.1) is exactly the mechanism B8 needs to infer which visibility tags apply to them. Concretely: **B8's item-bank selection logic needs a department → visibility-tag inference table**, not just a role → visibility-tag mapping, because "department" (marketing vs. engineering vs. legal) is what actually determines which tags a respondent can answer with real evidence, while "role" (leadership/department/employee) determines how many tags/how much of the pool they see. Full detail, sources, and reasoning: `claude/research-r9-functional-visibility-taxonomy.md`.

## 1.6 Working discipline — rules that govern how work happens on this project

These are standing rules established explicitly by Kartik across this thread. They are not suggestions; deviating from them without being told to is a process error, and any deviation that does happen (see the R4/R5/R6 note in Part 2) gets documented transparently rather than quietly absorbed as a new normal.

1. **Path A discipline (unchanged since before this thread):** never ship a classification, citation, or overlay that hasn't been checked against a primary or credible near-primary source. Tag findings [VERIFIED] / [REPORTED] / [UNVERIFIED] and date every citation. This applies to *external facts* (regulatory status, tool compliance claims, Big 4 framework content). It does not directly apply the same way to *newly authored assessment content* (e.g. R8's 33 drafted questions) — those are grounded in already-verified NIST subcategory (and, for part 2's MANAGE items, Playbook) text, but the actual question wording is original authorship, not a fact being verified, and needs a different kind of review: Kartik's judgment on quality and fit, not a source check.
2. **One research topic per run, as a default; narrow lookups may pair, max two.** Big-4-grade research means cross-checking against independent primary sources, tagging confidence, dating citations, and stating open questions rather than quietly resolving them — that discipline degrades when attention splits across topics. Exception: two narrow, low-complexity fact-lookups (e.g. two regulatory-status checks) may share a run; never mix a narrow lookup with a synthesis-heavy task. The ~95-tool verification backlog (R19) has its own rule regardless: batches of 5–8 tools per run, grouped by vendor family.
3. **Deviations from the pacing rule get documented, not normalized.** When Kartik explicitly directed three narrow lookups into one run (R4/R5/R6, one more than the stated cap of two), it was executed as directed, but the backlog explicitly notes it as a deviation from the default, with the cap stated as still two "unless he says otherwise for a specific run" — not silently treated as the new standard.
4. **After finishing each research task, check whether the next items can be paired without any quality tradeoff, and say so explicitly** — this is a standing habit Kartik asked for directly ("see if the next tasks can be clubbed and run together without any tradeoffs... do you understand? Answer in direct and 1 short sentence"), not a one-time instruction.
5. **This is not a strict "finish all research, then start all build" gate.** Research → High is foundational and the Build items gated on it are marked explicitly (see Part 2). Everything else in Build → High that isn't marked as gated has no research dependency and can start in parallel whenever work resumes on the Build side.
6. **Nothing on the Build list gets started until Kartik explicitly says so**, per his own instruction early in this thread ("only proceed to doing anything after I explicitly say so").
